# 19. 쿼리 줄이기, 요청마다 만들던 일꾼, 화면 빈자리 채우기 (2026-11-18)

## 한 줄 요약

세 번째 외부 리뷰(사용자 61점 · 팀장 77점)의 지적 중 사실인 것을 고쳤습니다. 공통점은 **"같은 일을 매번 다시 하고 있었다"** 입니다.

## 1. N+1: 30종목이면 SQL 30번

시장 지도는 시총 상위 30종목마다 업종을 물었습니다.

```java
// 전: 종목마다 한 번씩 → SQL 30번
stockMapper.findByCode(m.stockCode()).map(s -> s.sector())
// 후: IN (...) 한 번 → SQL 1번, 결과를 Map 에 담아 꺼내 씀
stockMapper.findByCodes(codes).forEach(s -> sectors.put(s.stockCode(), s.sector()));
```

## 2. 줄마다 하위 쿼리 3개 → 창 함수 한 번

글 목록의 종목 줄마다 "같은 소식 수·첫 기사·첫 언론사"를 하위 쿼리 3개로 따로 구했습니다(100줄이면 300번).
`COUNT(*) OVER (PARTITION BY ...)` 와 `ROW_NUMBER() OVER (... ORDER BY 발행 시각)` 로 **필요한 묶음만 한 번에** 모은 뒤 `LEFT JOIN` 으로 붙였습니다.
- `PARTITION BY` = "이 칸이 같은 줄끼리 묶어서"
- `ROW_NUMBER() ... = 1` = "묶음에서 가장 먼저 발행된 한 줄"

## 3. 정규식 대신 수집할 때 남긴 표시

홈 '전체'는 제목을 `REGEXP` 로 검사해 주요 공시만 골랐습니다(홈을 열 때마다 글 전부 검사).
그런데 `dart.py` 가 저장할 때 이미 `important()` 로 가르고, 일반 공시엔 `last_error = '일반 공시: LLM 요약 대상 아님'` 을 남깁니다.
→ SQL 은 그 표시만 봅니다. **같은 판단을 두 군데서 하지 않기** (18번의 "입력 가공은 한 함수로"와 같은 교훈).

## 4. 요청마다 만들던 스레드풀

`Executors.newFixedThreadPool(n)` 을 요청마다 만들고 닫았습니다. 스레드 만들기는 비쌉니다.
→ `QuoteService` 가 켜질 때 10명짜리를 한 번 만들고, 꺼질 때 `@PreDestroy` 로 닫습니다.

## 5. 화면 빈자리

- 시세가 꺼져 있으면 시장 지도 대신 **이슈 맵**(DB 의 뉴스 수·감성으로 그림)이 나옴 → `MarketMap` 의 `fallback`
- 종목 차트에 **하루 ±5% 넘게 움직인 날 ▲▼** (이미 있던 `/big-moves` API 연결). 누르면 그날 연결된 글, 글을 누르면 뉴스 탭에서 열림
- 홈 300건 넘는 글: 마지막 쪽에서 "이전 글 100건 더 받기"

## 리뷰가 틀린 곳

"종합 요약이 거부되면 다시 안 만든다"는 **의도된 설계**입니다(`step8_daily.py` `_save_stock` 설명: 같은 답을 받으러 LLM 을 또 부르지 않음, 사용자는 "다시 생성"으로 직접). 판단 보류만 새로 온 종목도 11/10에 고른 한계라 그대로 둡니다.

## 덧: CSS 를 고치면서 정리하는 법 (같은 날 오후)

덮어쓰기가 쌓인 CSS 에서 새 값을 또 파일 끝에 붙이면 같은 클래스 정의가 하나 더 늘어납니다. 대신

1. **먼저 화면이 안 바뀌는 정리만**: 선택자가 똑같은 규칙을 하나로 합치고, 모든 요소의 계산된 스타일을 전후로 비교 → 차이 0 이어야 함
2. **그다음 디자인 변경**: 고칠 클래스의 정의를 전부 찾아(`.x`, `.app-shell .x`, `.app-shell.dark-mode .x`) 기본 규칙 하나에 최종 값을 쓰고 나머지는 지움
3. 다시 비교 → 바뀐 요소가 내가 고친 클래스뿐인지 확인

"계산된 스타일" = 브라우저가 모든 규칙을 따진 뒤 실제로 쓰는 값 (`getComputedStyle`). 규칙이 어떻게 생겼든 이 값이 같으면 화면도 같습니다.
