# 14. 빈 화면과 실패 안내 (보완점 #6·#7·#8, 2026-11-12)

## 한 줄 요약

화면이 **"없다"** 고 말할 때 그게 정말 없는 건지, 아직 안 온 건지, 못 받은 건지 구별해 보여 준다. 세 가지를 고쳤다.
- 오늘 글이 없으면 빈 화면 대신 **가장 최근 날** 것을 "11/10 기준"으로 (#7)
- 서버에서 못 받으면 "없음" 대신 **"불러오지 못했습니다 · 다시 시도"** (#6)
- 수집기가 멈추면 화면 맨 위에 **"수집이 N분째 멈춰 있습니다"** (#8)

## 왜 필요한가

세 경우 모두 사용자에게는 똑같이 "비어 있음"으로 보였다. 가게 진열대가 비어 있을 때 "품절"인지, "아직 배송 전"인지, "창고 문이 잠김"인지 모르면 손님은 다시 올지 말지 정할 수 없다.

| 상황 | 고치기 전 화면 | 실제 |
|---|---|---|
| 이른 아침·주말 (11/11 아침에 본 것) | "오늘 0건 · AI 요약 없음" | 어제 자료는 멀쩡히 있음 |
| 서버가 잠깐 안 됨 | "오늘 AI 요약 없음" | 요약은 있는데 못 받음 |
| 수집기 꺼짐 (11/10 17:46 부터 929분) | 평소와 똑같음 | 15시간 동안 새 글이 없었음 |

## 들어가고 나오는 것

| | #7 최근 날 | #6 실패 안내 | #8 수집 멈춤 |
|---|---|---|---|
| 어디 | 백엔드 `StockService` + 화면 | 화면 `DashboardPageV7.jsx` | 화면 `adapters.js` |
| 들어감 | 오늘 날짜, DB 의 글·요약 | API 호출 결과 (성공/실패) | `/api/status` 의 `lastSuccessAt` |
| 나옴 | 응답 `date` (예: `2026-11-10`) | 안내 문구 + 다시 시도 버튼 | 경고 배너 (15분 넘으면) |
| 비용 | 0 | 0 | 0 |

## 코드 따라 읽기

### ① 오늘이 비면 최근 날 (`backend/.../stock/StockService.java` `getIssues`)

```java
LocalDate date = LocalDate.now(TimeUtils.KST);
List<StockIssueRow> rows = stockMapper.findIssues(date.atStartOfDay(), null, sourceType, limit);
if (rows.isEmpty()) {
    LocalDate latest = stockMapper.findLatestIssueDate(date.atStartOfDay(), sourceType);
    if (latest != null) {
        date = latest;
        rows = stockMapper.findIssues(latest.atStartOfDay(), latest.plusDays(1).atStartOfDay(), sourceType, limit);
    }
}
```

순서대로:
1. 먼저 평소처럼 "오늘 0시 ~ 지금"으로 센다. `to` 칸이 `null` 이면 끝 시각 없이 지금까지
2. 0건이면 "오늘 0시 전에 글이 있는 가장 최근 날"을 물어본다 (`findLatestIssueDate`, SQL 은 `DATE(MAX(published_at))`)
3. 그날 **하루만** (0시 이상, 다음 날 0시 미만) 다시 센다. 그 전날 글까지 섞이지 않게 끝을 막는다
4. 어느 날을 셌는지 `date` 로 돌려준다 → 화면이 "11/10 기준"이라고 쓸 수 있음

**SQL 에서 바뀐 것**은 조건 한 줄뿐이다 (`StockMapper.xml`):
```xml
<if test="to != null">
    AND a.published_at &lt; #{to}
</if>
```
MyBatis 의 `<if>` 는 값이 있을 때만 그 줄을 SQL 에 넣는다. 그래서 같은 쿼리를 "오늘~지금"과 "그날 하루" 두 가지로 쓴다. `&lt;` 는 XML 안이라 `<` 를 이렇게 쓴 것.

**종목 요약** (`getSummary`)도 같은 모양인데 조건이 하나 더 있다: 오늘 요약도 **없고** 오늘 글도 **없을 때만** 돌아간다. 오늘 글이 하나라도 있으면 요약이 아직 없어도 오늘 기준이다. 어제 요약을 오늘 것처럼 보여 주면 틀린 정보가 되기 때문.

**화면** (`adapters.js` `dayLabel`): 서버가 준 날짜가 오늘이면 "오늘", 아니면 "11/10".
```js
const kstToday = new Date(now.getTime() + 9 * 3600 * 1000).toISOString().slice(0, 10);
```
`toISOString()` 은 항상 영국 시간(UTC)이라 9시간을 더해 한국 날짜로 맞춘다. 안 더하면 한국 0시~9시 사이에 "어제"로 잘못 나온다 (시험에 0시 30분 경우를 넣은 이유).

### ② 실패를 "없음"과 구별 (`DashboardPageV7.jsx`)

종목 요약을 예로 들면, 받는 쪽에 **실패 기록**을 하나 더 둔다.
```js
const [summaryErrors, setSummaryErrors] = useState({});   // { 종목코드: true }
...
.then((res) => {
  setSummariesByStock(...);                                   // 받은 요약 저장
  setSummaryErrors((prev) => ({ ...prev, [code]: false }));   // 성공했으니 실패 표시 지움
})
.catch((err) => {
  if (err.name !== 'AbortError') {                             // 화면을 떠나서 취소한 건 실패가 아님
    setSummaryErrors((prev) => ({ ...prev, [code]: true }));
  }
});
```
그리고 화면 문구를 세 갈래로 나눈다: 요약 있음 → 요약, **실패 → "불러오지 못했습니다"**, 정말 없음 → "오늘 AI 요약 없음".

**다시 시도**는 숫자 하나로 한다:
```js
const [stockRetryTick, setStockRetryTick] = useState(0);
const retryStockPanels = () => setStockRetryTick((t) => t + 1);
...
}, [selectedStockCode, stockRetryTick]);   // useEffect 가 지켜보는 값
```
`useEffect` 는 지켜보는 값이 바뀌면 다시 돈다. 버튼이 숫자를 1 올리면 → 값이 바뀜 → 요청을 다시 보냄. 엘리베이터 버튼을 다시 누르는 것과 같다.

글 상세(`detailErrors`)도 같은 방식이고, 안내는 화면 3곳이 같이 쓰는 `ArticleDetail.jsx` 한 곳에만 넣었다.

### ③ 수집 멈춤 경고 (`adapters.js` `collectStaleMinutes`)

```js
export function collectStaleMinutes(lastSuccessAt, now = new Date()) {
  if (!lastSuccessAt) return 0;
  const minutes = Math.floor((now.getTime() - new Date(lastSuccessAt).getTime()) / 60000);
  return minutes > STALE_MIN ? minutes : 0;
}
```
수집은 5분마다 돈다. 마지막 성공이 15분(`STALE_MIN`, AI 점검 `health.py` 의 `GAP_MIN` 과 같은 값) 넘게 지났으면 멈춘 것으로 본다. 화면은 이미 1분마다 `/api/status` 를 받고 있어서 새 API 없이 숫자 비교만 더했다.

`now` 를 인자로 받는 이유: 시험에서 "지금"을 고정할 수 있다. `new Date()` 를 안에서 부르면 시험할 때마다 결과가 달라진다.

## 시험하다 걸린 함정: MyBatis 캐시

#7 시험을 처음엔 이렇게 썼다: 어제 글 넣기 → 조회(어제 날짜 확인) → **오늘 글 넣기 → 다시 조회(오늘 날짜 기대)**. 두 번째가 실패했다 (`expected 2026-11-12 but was 2026-11-11`).

이유: 백엔드 시험은 테스트 하나를 트랜잭션 하나로 묶는다 ([ApiTestSupport](../../../backend/src/test/java/com/hkteam2/stocknews/support/ApiTestSupport.java)). 같은 트랜잭션 안에서 MyBatis 는 **똑같은 쿼리·똑같은 값**이면 DB 에 다시 묻지 않고 처음 결과를 돌려준다 (1차 캐시). 시험은 글을 MyBatis 가 아니라 `JdbcTemplate` 으로 넣어서 MyBatis 는 데이터가 바뀐 걸 모른다.

해결: 시험을 둘로 나눔 (한 시험 = 한 번 조회). 실제 서버는 요청마다 새로 읽어서 이 문제가 없다.

**배울 점:** 시험이 틀렸다고 코드가 틀린 건 아니다. "실제로 그런가?"를 따로 확인해야 한다 (실제 서버 `curl` 로 삼성전자 요약이 `date 2026-11-10` 으로 오는 것을 봄).

## 한계

- "최근 거래일"이 아니라 "글이 있는 가장 최근 날"이다. 휴장일 달력이 없어서, 주말에 기사가 있으면 토·일이 나올 수 있다
- 수집 멈춤 경고는 **화면을 연 사람만** 본다. PC·Docker 가 통째로 꺼지면 화면도 안 뜬다. Slack 알림은 이 PC `.env` 에 웹훅 주소가 없어 안 간다
- 로그인이 필요한 동작(다시 생성·관심 종목)의 실패 문구는 아직 일반 "실패"다

## 확인 질문

**Q1.** 오늘 글이 0건이라 어제 하루로 셀 때, 왜 "어제 0시 이후 전부"가 아니라 "어제 0시~오늘 0시"로 끝을 막나?
<details><summary>▶ 답 보기</summary>

"11/10 기준"이라는 표시와 숫자가 맞아야 한다. 하루로 딱 잘라야 "11/10 기준 글 5건"이 정확히 그날 5건이 된다.
</details>

**Q2.** 종목 요약은 오늘 글이 하나라도 있으면 어제 요약이 있어도 왜 보여 주지 않나?
<details><summary>▶ 답 보기</summary>

화면은 "오늘 글" 기준 감성 비율과 요약을 같이 보여 준다. 오늘 글이 있는데 어제 요약을 붙이면 오늘 소식과 맞지 않는 요약이 오늘 것처럼 보인다. 요약은 1시간마다 만들어지니 조금 기다리면 오늘 것이 생긴다.
</details>

**Q3.** `catch` 에서 `AbortError` 는 왜 실패로 치지 않나?
<details><summary>▶ 답 보기</summary>

사용자가 다른 종목으로 넘어가면 앞 요청을 일부러 취소한다 (`AbortController`). 이건 고장이 아니라 정상 동작이라, 실패 안내를 띄우면 헛경보가 된다.
</details>

**Q4.** 다시 시도 버튼은 왜 요청 함수를 직접 부르지 않고 숫자를 올리나?
<details><summary>▶ 답 보기</summary>

요청은 이미 `useEffect` 안에 있고, 거기에 취소(`AbortController`)·결과 저장이 다 들어 있다. 숫자를 올려 그 `useEffect` 를 한 번 더 돌게 하면 같은 코드를 두 번 쓰지 않아도 된다.
</details>

**Q5.** 시험에서 두 번째 조회가 옛 결과를 준 이유는?
<details><summary>▶ 답 보기</summary>

같은 트랜잭션 안에서 MyBatis 가 같은 쿼리·같은 값의 결과를 기억해 두고(1차 캐시) 다시 준다. 글은 `JdbcTemplate` 으로 넣어서 MyBatis 가 바뀐 걸 몰랐다. 실제 서버는 요청마다 새로 읽으므로 상관없다.
</details>
